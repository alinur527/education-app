Read `frontend-design/SKILL.md`, `docs/DESIGN.md`, then-current React feature components and baseline screenshots at the paths `docs/screenshots/dashboard-desktop.png`, `docs/screenshots/phase2/cms-320.png`, `docs/screenshots/phase2/student-lesson.png`. ### Pass 1: task and reading hierarchy

Retain ink `#172544`, secondary `#53627A`, action `#315AE8`, workspace `#F4F6FA`, paper `#FFFFFF`, success `#21735B`. Keep self-hosted Golos Text, existing 12/14/16/20/28/40 scale, 68ch reading measure and 4/8/12/16/24/32/48 spacing. Left-align text and controls. Status needs words as well as color.

The memorable surface should be a real study invitation: today's next lesson, estimated planned minutes and one clear action. Place uncompleted work and the next deadline above broad analytics. Preserve the book illustration for a new account's first action, then reduce its area when there is actual work. Avoid adding another KPI hero: the baseline already repeats accuracy in the main summary and the side card.

```
Desktop
Navigation | Today: next topic + Open lesson      | Next deadline
           | Today / Week / Month agenda           | Reminders
           | Chosen ENT subjects, with readiness   | Saved reading
           | Recent attempts + Open result

Mobile
Header + language
Next useful task + primary action
Agenda list / compact date selector
Chosen subjects and truthful material readiness
Bottom navigation; secondary destinations in a labeled More menu

Teacher
Course / Group context | Waiting for review + due date
Content hierarchy     | Bilingual editor / preview
                      | Selected file + progress + retry
                      | Save draft / Review / Publish
```

The current lesson screenshot uses a generic page title “Урок” followed by the real title inside a wide panel. Promote the lesson title into the page heading, keep course/module breadcrumbs, and constrain long theory text. Keep materials and the next practice action near the end of the relevant reading section. A saved-reading state should say exactly what is saved and when; it should not imply private assignments work offline.

### Pass 2: critique and control detail

The first layout risks becoming a generic productivity dashboard. Tighten it around the ENT loop: each plan task has a subject/topic, a specific reading/practice action and a reason such as recent mistakes; planned minutes are clearly an estimate. Use an agenda list as the mobile default instead of squeezing a seven-column interactive calendar into 320px. Do not add empty time slots or infer completion from a past date.

The current mobile CMS is legible, but paired RU/KZ fields and all block controls create a long form. Preserve explicit save state, offer compact language switching with visible missing-translation counts, keep the content hierarchy contextual, and let preview use the same safe student renderer. A sticky action region must sit above the mobile navigation and must not hide the focused field. Never clear chosen files or text after a failed request.

For uploads, show selected filename, allowed size, actual byte progress where measurable, completion, and retry. Provide ordinary file picking beside drag/drop. For assignments, show deadline/timezone, file limits and the exact resubmission effect before sending; keep the grade feedback next to the submitted answer. For charts, use one compact real history with a text equivalent and visible zero scores. For transitions, animate only state changes; `prefers-reduced-motion` removes nonessential movement.

After implementation, compare the same student/teacher states at 320/390/768/1024/1440, including long Kazakh labels, keyboard focus, calendar/date controls, upload failure, stale revision, offline return and no-data screens. Automated axe results supplement manual focus/reading checks; they are not accessibility certification.

### Practical implications for the content release

1. Use the official specification for coverage/version, and independent subject references for facts and explanations. Source existence is not correctness: the iTest defects above are a concrete reason for question-level checking.
2. Write original RU/KZ teaching explanations and original training questions; preserve `AI_GENERATED` origin when generated by the assistant. Do not label catalog metadata as theory or claim human verification that did not occur.
3. Links to paid or unavailable resources can supplement a lesson, but they cannot count as its required complete theory, practice, file or publication coverage.
4. Keep `accessStatus`, `reuseMode` and `reviewStatus` separate. A public preview may still be link-only; a publisher listing may be valid bibliography while offering no inspected content. Full downloaded-file byte size/hash/storage evidence belongs to the controlled ingestion manifest, not this research table.
